# Chat page

Everything the chat page does: projects, skills, commands, tools, MCP servers and voice. Back to the [README](../README.md).

**On the hosted server, a stdio server starts when you first use it.** The 1 GB Machine can't have Playwright's browser and the npx servers all in memory at boot, so hosted stdio servers remember their tool list next to `mcp-servers.json`, start on the first call and stop again after five idle minutes. The Tools page still lists their tools as connected.

## Chat

<http://localhost:3000/chat> (also `/ui/chat.html`) is a chat page that sends through the Interceptor like any other client, so the Router picks the model unless you name one. Pages answer without `.html` too, and each chat has its own address (`/chat#c=<id>`, or the old `/chat.html#chat=<id>`, which is rewritten on open), so Back and Forward work and the address can be bookmarked or shared. What it does:

- **Live progress.** Each reply shows its steps as they happen: the Router choosing, the model it picked and why, the transforms applied, the Gateway's answer (with fallbacks and the model that actually served it), time to first token and tokens per second. A **Details** line under each reply opens the same steps again for a reply you scrolled past. The **Activity** panel is a drawer over the right edge (like the settings drawer) showing every request through the harness live, from this page and from other clients such as Claude Code, plus the health of each part. Both come from `/ui/api/live`, a Server-Sent Events feed of the routing log.
- **Notifies you when it needs you.** With notifications turned on (Options → Tools → Notifications, or Settings → Notifications; per device and per kind), the browser shows a notification while the page is in the background when a guard approval is waiting, a run needs a decision, or a reply has finished. They say only what happened, never what was said or run, and nothing is pushed from the server: they fire while a harness page is open.
- **Settings drawer.** The sliders button in the chat bar opens the chat's settings as a drawer over the right edge (a full-screen sheet on phones), so the conversation stays where it is. It has four tabs: **Model**, **Context**, **Tools** and **Voice**; the last tab you used is remembered, the arrow keys move between tabs, and Esc, the × or (on a phone) the dimmed area closes it. Wherever this page says *Options*, it means this drawer.
- **Chats.** Every chat is saved in the browser and listed on the left under **Recent**, newest first, with search. Alt+↑/↓ moves between chats, Ctrl+Shift+O starts a new one, Ctrl+K searches. A chat that is replying shows what it is doing in the list (routing, thinking, writing with a token count, or the tool it is using), and one that finished while you were elsewhere gets a dot. After the first reply, the model is asked for a short name for the chat (turn this off under Options → Model **Name new chats automatically**; type a title to rename it yourself). Hover a chat to show its × delete button, or use the trash button in the top bar, or **Delete all chats** under the list.
- **Projects.** The **+** next to *Projects* in the sidebar makes one: a name, a colour, instructions sent with every chat in it, skills that are on for every chat in it, and optionally a git repo its chats can read. Click a project to see only its chats; **New chat** then starts one inside it. Move a chat into or out of a project under Options → Context. The project's settings (the gear on hover, or its badge in the top bar) also show its total tokens and cost. Deleting a project keeps its chats.
- **Scheduled messages.** The **+** next to *Scheduled* sends a message at a set time, once or every hour, day, weekday or week, into a new chat each time (optionally in a project) or into an existing chat. They run while Bright Chat is open in a browser tab; a run missed while it was closed happens as soon as the page opens. **On a hosted server with a database** the server sends them itself, with every tab closed (see [Scheduled messages on the server](fly.md#scheduled-messages-on-the-server)). **Run now** in a schedule sends it straight away.
- **Skills.** A skill is named instructions: a review checklist, a writing style, the steps for a task. The sparkle button in the message box lists them: tick one to turn it on for this chat. **Manage skills** adds and edits them (three examples are added the first time), and **Import from Claude Code** lists the skills in `.claude/skills` in this repo and your home folder to pull in with one press. **Let the model load other skills when it needs them** gives the model a `use_skill` tool and a list of your skills, so it can read one when a question matches; like any tool, this sends requests to tool-capable models.
- **Commands.** Typing `/` in the message box lists the commands the page handles itself, then your own, each with the model it sends to, and under them the tools this chat can use. **`/advisor MODEL`** sets a better model this chat's model may call for a second opinion: give it a short name (`/advisor opus` finds the newest Opus) or a full one, and from then on the chat's model has an `ask_advisor` tool it can hand a hard part to. The advisor answers in words, with no tools of its own, so the expensive model's part stays small; each call's cost is counted with the reply that made it. `/advisor` alone says what is set and `/advisor off` removes it; the composer says which advisor a chat has. A short name is matched to the newest model the Gateway serves, so "opus" means `claude-opus-5.5` and "opus-4.5" the one it names. **`/model NAME`** switches what the chat answers with, the same as the "Answer with" picker: a model by a short or partial name (`/model opus`, `/model gpt mini`) or a strategy by name (`default` and `auto` too); `/model` alone lists the choices. After `/advisor`, `/model` and the model word of `/subagent`, the box shows the Gateway's models that fit what you have typed, newest first; Up/Down and Tab or Enter pick one. A Gateway name ending in `-latest` (like `or-claude-opus-latest`) counts as the newest of its family. **`/subagent TASK`** hands one task to an agent on its own branch while the chat carries on: it is an ordinary run, so it has its own page entry, approvals and diff, and follows the chat's repo, routing and effort. **`/agent [NAME] TASK`** gives the task to a standing agent on the Agents page instead (one of the project's agents, with the chat's last messages as context; see [Persistent agents](task-runner.md#persistent-agents)). `/subagent MODEL TASK` gives it a model of its own; use this when a cheaper model can handle searching, fetching or a mechanical edit. **`/plan TASK`** starts a plan-only run: the agent reads the repo and writes down what it would change, in order, without changing files or committing. Your own commands are one message sent with a model, strategy or effort for that turn only, so the next message goes back to the chat's own routing. The panel's **Commands** button adds and edits them (a name, one line on what it does, the model or strategy, the effort, and the message), and **Import from Claude Code** lists the commands in `.claude/commands` in this repo and your home folder to pull in with one press. The message is where `{args}` becomes what you type after the command (a command with no `{args}` gets it after its message). A command's turn carries no tools, since a model named there may not call them.
- **Queued messages and following a reply.** Type while a reply is still arriving and the message waits its turn instead of being dropped: the composer says how many are waiting, and **Clear** removes them. Scrolling up during a reply stops the conversation following the new text, so you can read what came before; a button at the bottom takes you back, and the chat follows again once you are at the end. Scrolling up inside a thinking pane holds that pane still in the same way. A reply that was still arriving when the page closed is marked as cut off, instead of its animation playing forever.
- **Stop, resend and frozen replies.** A reply in progress has a **Stop** button (or press Esc), and every message you sent has a resend button. The Interceptor already fails a request that gets no answer within 5 minutes or goes quiet for 2 (see `gatewayTimeoutMs` and `streamIdleTimeoutMs`); as a backstop, for example when the Interceptor itself stops answering, the page gives up after 310 and 130 seconds and offers Retry. Change both under Options → Model (0 waits forever). Free models often stall or return HTTP 429 once their daily or per-minute quota is used up, and the error says so.
- **Costs and context.** Each reply shows what it cost (`free` for free and local models), the model that wrote it under the reply, and the top bar shows the chat's tokens, total cost and how full the model's context window is for the next message. Click those numbers for a breakdown: a bar per reply (sent and written tokens), tokens and cost by model, the size of the next message against the model's context window, and the project's totals. Prices and context sizes come from the Gateway's `/v1/model/info` through `/ui/api/model-info`; a provider's own figure (OpenRouter's `usage.cost`, LiteLLM's `x-litellm-response-cost` header) wins when there is one.
- **Formatting and copying.** Replies render Markdown (headings, lists, tables, quotes, highlighted code). Every message has a copy button, and so does every code block. Messages can be edited and resent, and the last reply regenerated.
- **Export.** Download a chat as Markdown, copy it, or export every chat into one file.
- **Context.** Attach text files and images with the paperclip, by dropping them on the page, or by pasting. Under Options, each chat has a system prompt and notes the model sees with every message. The composer shows a rough token count for the request.
- **Strategy per chat.** Options → Model → **Strategy for this chat** picks where the chat's messages go: the default strategy, one of your named strategies from the Routing page, or **One model directly** to skip routing and send every message to the model you type. A project has the same choice in its settings, and its chats follow it unless they pick their own. Each reply says which strategy it used.
- **Tools.** A chat can use MCP servers and read a git repo on your computer. See [Chat tools: MCP servers and git repos](#chat-tools-mcp-servers-and-git-repos).
- **Voice.** The mic button (Ctrl+M) dictates into the message box, optionally sending when you stop talking. Replies can be read aloud on demand or automatically as they stream, with a choice of voice, speed, pitch and volume, and a Test button to hear a voice. Hands-free mode does both in a loop: turn it on with the headset button next to the mic (or under Options → Voice). It starts listening at once, sends when you pause, reads the reply aloud, then listens again; click it again to stop listening and reading. **Read clearly** (on by default) says symbols, shorthand and code names as words: `->` becomes "to", `e.g.` "for example", `10k` "10 thousand", `max_tokens` "max tokens", and a link becomes "a link to github.com". Dictation uses the browser's speech recognition (Chrome and Edge have one; they send the audio to their speech service), or the harness's own speech model when the browser has none. **Options → Voice → Dictation** picks one: **Auto** (the browser, else the server), **This browser**, or **Speech model**. Brave and some Chromium builds have no speech service and answer every attempt with `network`; with `OPENROUTER_API_KEY` in `.env` they fall back to it on their own. The microphone only works on `http://localhost` or https.

**Dictation through the harness.** With `OPENROUTER_API_KEY` set, `/ui/api/stt` sends the recording to OpenRouter's [speech-to-text models](https://openrouter.ai/collections/speech-to-text-models); it starts on the cheap Mistral Voxtral Mini Transcribe. `STT_URL` points it at another OpenAI-style server instead (Groq's free Whisper, OpenAI, a local Whisper, or a model in LiteLLM at `http://localhost:4000/v1`). The page records in short stretches, ends one when you pause, and adds each transcript to the message box. On Android (where the recognizer keeps repeating, or drops a phrase if a pause comes too soon) it listens **one phrase at a time**: it ends each phrase on a pause and starts a fresh recognizer for the next, instead of one long session. If an error is descriptive it is shown in plain words (`[object Object]` never appears), and a recognizer that returns empty too many times gives up with a message rather than looping. The speech model uses the same OpenRouter credential as the read-aloud voice (connect it once on the Users page or with `OPENROUTER_API_KEY`), a slow server is cut off after 45 seconds with a plain "timed out" message rather than a raw error, and a proxy error is shown in words instead of its HTML.

## Chat tools: MCP servers and git repos

The chat page can give the model tools. While it answers, the model can call them, see what they return, and keep going. Each call shows in the reply as a line you can click to see what was sent and what came back.

**Link a chat to a git repo.** Under Options → Tools, type the path of a folder inside a git repo on this computer (for example `C:\Users\you\code\my-project`) and press **Link**. Each chat has its own link. The model then gets read-only tools to list, read and search the repo's files (`git grep`), and to look at `git status`, the log, diffs and single commits. It can't change files, commit or push. Files that `.gitignore` covers are not listed, paths outside the repo and the `.git` folder are refused, and git must be installed. **On a hosted server this is off** (there are no folders of your own there, and no shell): the page says so and the path field is hidden, so attach a GitHub repo instead. `HARNESS_LOCAL_REPOS=1` turns folder repos and the shell back on where the harness runs on your own computer. A Windows path on a server that is not Windows is refused with a plain reason.

**Attach a GitHub repo to a chat.** Under Options → Tools, **GitHub repo** lists the repos your GitHub account lets the harness reach; pick one (or type `owner/name`) and press **Attach**. The model reads it through GitHub's API (nothing is cloned, so it works on a hosted server): `github_list_files`, `github_read_file`, `github_search`, `github_log`, `github_branches`, `github_list_issues`, `github_get_issue`, and for GitHub Actions `github_list_workflows`, `github_list_runs`, `github_get_run` (jobs and the failing step) and `github_job_logs` (the end of a job's log). It can also open an issue, comment, or open a pull request from a branch that already exists (`github_create_issue`, `github_comment`, `github_create_pull_request`), or start, re-run or cancel a workflow (`github_run_workflow`, which needs a `workflow_dispatch` trigger, `github_rerun`, `github_cancel_run`). Each of those waits in the chat for your **Allow** and shows exactly what would be posted; the server refuses them without that confirmation. It cannot push code or edit files. Press **Connect GitHub** once to link your account (the same connection **Agents > GitHub** uses for Runs); on your own computer with no sign-in, a `GITHUB_TOKEN` in `.env` is used instead. A chat can have both a local repo and a GitHub repo. Setting it up on a server: [Connect GitHub](fly.md#connect-github).

**MCP servers, from the page.** Open **Tools** (a link on the Settings page, or Manage in the chat Options). **Add a server** takes a program (`npx`/`uvx` command, arguments, environment variables) or a web address (HTTP or SSE, with headers). **Test connection** connects without saving and lists the tools, or says what is wrong (for example that `uvx` isn't installed). **Popular servers** adds Memory, Fetch, Playwright and others in one click, or (**Set up…**) opens a guided setup for ones that need a folder or a key: what the server needs, where to get it (a link to the sign-up page), a **Test connection**, then **Add** (or **Add anyway** if the test failed). Each server has an on/off switch and a tick per tool, so the model is offered only what you leave on. **Ask me before a tool runs** (Never, Tools that change something, Every tool) makes the chat show the tool's input and wait for your **Allow** before it runs; the server refuses the call without that confirmation. "Change" means any tool the server doesn't mark read-only, so a server that marks nothing asks every time. In `mcp-servers.json` it is `"askBefore": "writes"` or `"all"`. Saved values of environment variables and headers are never shown again (type a new one to replace it), and `${NAME}` references are shown as they are. Only admins, or this machine, can change servers, because a program server runs a command here. The page edits `mcp-servers.json`, so everything below still applies.

**Connecting GitHub.** **Connect GitHub** opens a small dialog only when it is needed (paste a fine-grained token with Contents: read and write); once connected the page shows one quiet line instead of a full form. A subagent can use a GitHub-only chat on any server.

**Vercel.** The **Vercel** entry in Popular servers connects Vercel's hosted MCP server (`https://mcp.vercel.com`) so a chat can read your projects, deployments, build and runtime logs, domains and environment variables, and help with deploys. Create an access token in Vercel (Account Settings, Tokens), put it in `.env` as `VERCEL_TOKEN`, and add the entry; it sends `Authorization: Bearer ${VERCEL_TOKEN}` and is set to ask before anything that changes your account (deploying, environment variables, domains, DNS, project settings). The token reaches everything your Vercel account can, so scope it to one team and delete it when you stop using it. Vercel's server may accept sign-in only from approved apps (OAuth), in which case it refuses a token; **Test connection** then shows the error. This harness has no OAuth sign-in for MCP servers yet. The entry has not been tried against the real Vercel server.

**Wolfram Alpha.** The **Wolfram Alpha** entry in Popular servers connects the community `wolfram-mcp` server so a chat can compute and look up facts: maths, units, dates, chemistry, and the "what is" questions that want a computable answer. It needs a Wolfram AppID; the Tools page's guided setup (**Set up…**) links to the [Wolfram Alpha developer portal](https://developer.wolframalpha.com/access) (sign in with a free Wolfram ID, press **Get an AppID** and choose the LLM API) and adds the server with `WOLFRAM_APP_ID` set. There are free and paid plans; the free one is rate-limited but enough to try it.

**MCP servers, from the file.** Copy `mcp-servers.example.json` to `mcp-servers.json` next to `server.js` and list your servers. The layout is the same as Claude Code's `.mcp.json`, so you can copy entries from there:

```json
{
  "mcpServers": {
    "filesystem": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "${HOME}/Documents"] },
    "github": { "type": "http", "url": "https://api.githubcopilot.com/mcp/", "headers": { "Authorization": "Bearer ${GITHUB_TOKEN}" } }
  }
}
```

- A server with a `command` is started by the Interceptor and talks over stdio. One with a `url` is reached over HTTP (`"type": "http"`, the default for a `url`) or SSE (`"type": "sse"`).
- `${NAME}` and `${NAME:-default}` are filled in from your environment and `.env`, so keys can stay in `.env`. `${HOME}` is your home folder (also on Windows) and `${HARNESS_DIR}` is this repo's folder. A `${NAME}` with no value and no default stops that server with a message naming it. `mcp-servers.json` is gitignored anyway.
- The example file works as it is: `filesystem` (your `Documents` folder; change the path, and the folder must exist) and `jev-files` (needs the harness running) are on, `fetch` (needs [uv](https://docs.astral.sh/uv/)) and `github` (needs `GITHUB_TOKEN` in `.env`) are off until you remove `"disabled"`. Servers start in the repo folder, so `scripts/jev-files-mcp.js` needs no full path, and they get your whole environment (proxy and npm settings included). If a program such as `npx` or `uvx` isn't installed, the error says which one to install.
- `"disabled": true` keeps a server listed but not started. `"disabledTools": ["name", ...]` leaves those tools of a running server out of the chat (the Tools page's ticks).
- Slow or failing servers: each server connects on its own, so one that fails never holds up the others. Servers started with `npx`, `uvx` or `docker` get 120 s to connect (they download the package the first time) and one more try after a timeout; others get 30 s and no retry. Change this per server with `"timeoutMs"` (connect and list tools), `"retries"` (more tries after a timeout) and `"callTimeoutMs"` (one tool call, 120 s by default). A failed server's error says what to do: a timeout says to run its command once in a terminal to warm the cache, a 404 means the `url` is wrong or the service was removed (fix it or set `"disabled": true`), 401/403 means check its `headers`.
- You don't need an MCP entry for Artificial Analysis: model ratings come from `ARTIFICIAL_ANALYSIS_API_KEY` in `.env`.
- The Interceptor connects when it starts and prints each server's state. Options → Tools lists them with their tool counts and any start-up error. Untick a server to leave its tools out of your chats. Press **Reload** after editing the file.

Requests carry tools only when a chat is linked to a repo or an MCP server is ticked. Requests with tools go to a model that can call them (the Router's `strong_model_tools` or `weak_model_tools`, falling back to the strong model), not to the free chat model. Each round of tool calls is its own request through the Interceptor, so it is routed, logged and counted like any other. The reply's cost and token counts add up all of the rounds. A round that comes back with nothing at all — no text and no tool call, which is what a model that spends its whole answer thinking does — is tried once more, with twice the output room when the cap cut it off. If the second try is empty too, the reply says why (the output cap, the content filter, a tool call that arrived with no name, or that no tool list could be loaded) instead of leaving an empty bubble. **Max tool rounds** in the chat options sets how many rounds of tool calls a reply may use, and **0 means no limit** (the default): the reply goes on until the model stops calling tools or you press Stop, with the stall and no-reply timeouts still applying. Only rounds that really ran tools count towards it, not the empty-round retry. Tool results pass through Headroom like Claude Code's, so long results are trimmed to about 12,000 characters when Headroom is on.

Tools run only for requests from this computer (`/ui/api/tools/call` refuses others), and only the chat page uses them. Claude Code connects to its own MCP servers (`claude mcp add ...`), and its tool calls pass through the harness unchanged.

## Read-aloud voices

Under Options → Voice, **Read aloud with** chooses between a speech model and the browser's own voices.

**Speech model (the default).** With `OPENROUTER_API_KEY` in `.env`, the harness offers every [OpenRouter speech model](https://openrouter.ai/collections/text-to-speech-models) in the **Speech model** menu, with each model's voices in the **Voice** menu. It starts on the free Fish Audio model; paid ones include Kokoro ($0.62 per million characters), Gemini Flash TTS, Microsoft MAI Voice and ElevenLabs. Your choice is saved in the browser. The page reads in pieces: a short first one so speech starts quickly, then longer ones, and it fetches only the piece after the one playing, so stopping early saves the rest of the speech tokens.

**Browser voices.** Free and offline, but quality depends on the browser: Edge on Windows has the best (the "Online (Natural)" voices, marked ★ and picked by default), Chrome has "Google" voices, and the built-in Windows voices sound robotic.

Optional `.env` settings:

| Setting | What it does |
|---|---|
| `TTS_URL` | Use another OpenAI-style speech server instead of OpenRouter: [Kokoro](https://github.com/remsky/Kokoro-FastAPI) locally (`docker run -p 8880:8880 ghcr.io/remsky/kokoro-fastapi-cpu:latest`, then `http://localhost:8880/v1`), OpenAI (`https://api.openai.com/v1` with `TTS_API_KEY`), or a TTS model in LiteLLM (`http://localhost:4000/v1`). |
| `TTS_MODEL`, `TTS_VOICE` | The default model and voice before you pick in the page. |
| `TTS_API_KEY` | Key for `TTS_URL`. Not needed for OpenRouter or the Gateway. |
| `TTS_VOICES` | Comma-separated voices for the default model, when the server doesn't list them. |
| `TTS_INSTRUCTIONS` | Tone and pacing for models that take it (OpenAI, Gemini, Fish Audio), e.g. `Calm, friendly, a little brisk`. |
| `STT_URL` | Use another OpenAI-style server for dictation instead of OpenRouter: Groq's Whisper (`https://api.groq.com/openai/v1`), OpenAI (`https://api.openai.com/v1` with `STT_API_KEY`), a local Whisper server, or a model in LiteLLM (`http://localhost:4000/v1`). |
| `STT_MODEL`, `STT_LANGUAGE` | The transcription model and its default language. |
| `STT_API_KEY` | Key for `STT_URL`. Not needed for OpenRouter or the Gateway. |
