# Model Layer audit: does it work as the README claims?

Research for [#4](https://github.com/skyfly200/custom-ai-harness/issues/4) (map: #3). Researched 2026-09-24. Nothing was run end to end. Every verdict comes from reading the source code or docs that own the behaviour, and each one links to that source. The one computed number (the threshold calibration) comes from RouteLLM's own published dataset.

**Model Layer** = Interceptor (`server.js`, :3000) → Router (RouteLLM, :6060) → Gateway (LiteLLM, `config.yaml`, :4000) → provider.

Source versions checked:

- RouteLLM `main` @ [`0b64fda`](https://github.com/lm-sys/RouteLLM/tree/0b64fdafe049e596a3f5657c219329f24af24198). The last commit was 2024-08-09, so the project is effectively unmaintained. I diffed the PyPI release `routellm==0.2.0` (the latest, uploaded 2024-07-08) against it. `controller.py` and `routers/routers.py` are identical. `openai_server.py` differs only in that `main` adds `GET /health`.
- LiteLLM `main` @ [`1c8a0ff`](https://github.com/BerriAI/litellm/tree/1c8a0ff6023b3eba6b01e955c49edcfa97bf0d22), plus the docs at docs.litellm.ai.
- The repo at `ddcec18` (master).

## TL;DR

The Model Layer **does not work as documented**. There are two hard blockers on the path, and either one alone stops routing:

1. **The RouteLLM launch command is wrong.** `--config` takes a map of *router name → checkpoint kwargs*. It is not a place to put routing targets. Every key in `routellm-config.yaml` is ignored. `--routers` defaults to `random`, so every `router-bert-*` request comes back as HTTP 400 `Invalid router bert`. If you add `--routers bert`, the server crashes at startup because the supplied config has no `bert:` key. The strong and weak models fall back to `gpt-4-1106-preview` and Anyscale Mixtral.
2. **RouteLLM's request schema rejects normal agent traffic.** `tools` is typed `List[Dict[str, str|int|float]]`, so any OpenAI tool definition, which has a nested `function` object, fails validation with a 422. Assistant messages with `content: null` also fail.

On top of that, **Claude Code cannot talk to this stack at all**. Claude Code speaks only the Anthropic Messages format (`/v1/messages`), and the Interceptor only proxies `/chat/completions`. The Interceptor's thresholds (0.2/0.5/0.8) are not calibrated for `bert`. Against RouteLLM's own calibration data they send about 91%, 22% and 1.4% of prompts to the strong model.

The Gateway (LiteLLM) config is mostly sound. `openrouter/openrouter/free` and `groq/openai/gpt-oss-20b` are valid IDs, and `litellm_settings.fallbacks` works (it's a legacy placement). `general_settings.port` is not a real setting, but it is harmless because 4000 is the default anyway.

**BERT threshold calibration** (computed from the dataset above, using the same quantile rule as `calibrate_threshold.py`):

| Threshold | Share routed to strong |
|---|---|
| 0.20 (the Interceptor's "complex") | **90.7%** |
| 0.50 (the Interceptor's "balanced") | **21.7%** |
| 0.80 (the Interceptor's "simple") | **1.4%** |

| Target strong share | bert threshold |
|---|---|
| 90% | 0.2077 |
| 80% | 0.2865 |
| 70% | 0.3372 |
| 50% | 0.4066 |
| 30% | 0.4651 |
| 20% | 0.5094 |
| 10% | 0.5949 |

The `bert` score distribution has mean 0.406, sd 0.152, IQR 0.313–0.485 and max 0.927. Nearly all the useful range sits between 0.2 and 0.6. That makes 0.8 effectively "always weak" and 0.2 effectively "always strong". The "balanced" default of 0.5 is not 50/50; it sends about 22% to strong. All of this is calibrated on Chatbot Arena chat prompts, not coding-agent traffic, so real shares will differ. RouteLLM itself says to calibrate on a sample of your own queries.

## What a working invocation would look like (not applied; research only)

This follows R1–R4 and R6. It is not tested.

```bash
pip install "litellm[proxy]" "routellm[serve]"       # or separate venvs if numpy<2 conflicts
export OPENAI_API_KEY=dummy                          # RouteLLM builds OpenAI() clients at import
python -m routellm.openai_server --routers bert \
  --strong-model openai/claude-sonnet-5 --weak-model openai/fallback-groq \
  --base-url http://localhost:4000/v1 --api-key dummy --port 6060
# omit --config (uses the built-in bert checkpoint), or pass a file containing:
#   bert: { checkpoint_path: routellm/bert_gpt4_augmented }
```

Even so, R10 (tool-bearing requests → 422) remains. Fixing it means either patching or forking RouteLLM's request model, or moving routing out of the request path. One option is to call `Controller.route()` / `calculate_strong_win_rate` from a sidecar and let the Interceptor pick the LiteLLM model name itself. That is a design question for the map, not something this ticket settles.

## Open decisions surfaced (for the map, not decided here)

1. **What occupies :8000**: the local llama/vLLM engine, or a Claude CLI wrapper that doesn't exist yet? The Tier 1 `model_name`s depend on the answer.
2. **Does RouteLLM stay in the request path?** Given R9, R10 and the fact that the project is unmaintained, the alternatives are a sidecar scorer, or keywords/heuristics plus LiteLLM routing alone.
3. **Which client protocol is primary?** Supporting Claude Code needs an Anthropic `/v1/messages` front door (LiteLLM exposes one), and the docs say non-Claude models behind it are unsupported.
4. **Threshold policy**: pick a target strong share and derive thresholds from calibration (table above), ideally on sampled coding-agent prompts, rather than fixed 0.2/0.5/0.8.
