How to use this page

This page is a map of where every request goes. Boxes are the parts of the harness; lines are the routes between them. Change the lines and boxes, then press Save.

  1. Follow a request from left to right. It enters at Request (the Interceptor), goes through Compression (tick what should shrink it), then to the Router. The Router scores how hard it is and sends it out of one of its outputs (Strong, Strong with tools, Weak, Weak with tools, Weak over a size limit) to a model box. A model box is a name the Gateway serves; inside it, Served by lists the provider models that actually answer.
  2. Add more tiers. Strong and Weak are two tiers; + Add tier on the Router adds another with its own model and a score it starts from. Requests scoring at or above it, and below the next tier up, go to it: one above the threshold catches the hardest requests (a frontier model), one below it the middling ones. Each tier can have its own model for requests with tools. Has an image sends pictures to a model that reads them. In chats, the Effort button next to Send moves requests toward cheaper or better tiers; other clients send the header x-harness-effort (min, low, high or max).
  3. Compare models. Each model box shows its quality (0 to 100), price per million tokens, speed and strengths. With ARTIFICIAL_ANALYSIS_API_KEY in .env they come from Artificial Analysis’s benchmarks; otherwise type them with Edit. The Router warns when a higher tier’s model scores lower than the one below it.
  4. Change where a route goes by dragging from the dot on the right of an output to a model box. Each output goes to one model, so the new line replaces the old one.
  5. Set fallbacks by dragging a model's If it fails dot to another model. When a model errors, hits a rate limit or times out, the Gateway tries its fallbacks from the top. Reorder them with ↑ ↓, and hover a model to see its fallback lines clearly.
  6. Add a model with Add model above: give it a name, pick where it runs (OpenRouter, Groq, Ollama…) and the model id. For OpenRouter you can search its whole model list in the dialog, filter to free or tool-capable models, and click one to fill in the id. To give an existing model a second provider model, use + Add provider model in its box; the Gateway then shares requests between them.
  7. Remove things: Clear unconnected models removes every model box that no route reaches in any routing, directly or through fallbacks (those boxes are dashed and say so); press and hold × in a model's title to remove the whole model; × next to a provider model removes just that one; click a line and press Delete (or Remove connection) to remove a route.
  8. Use different routings for different chats. New routing copies the one shown under a new name; change its lines, compression and tools, then Save. In Bright Chat, pick it per chat in Options or per project in its settings, or choose One model directly to skip routing. Model boxes are shared by every routing. Fallback lines are the Gateway's until you change one while a routing is shown: that routing then keeps its own (Use Gateway fallbacks drops them). Other clients pick one with the header x-harness-profile.
  9. Tools lists the MCP servers from mcp-servers.json. Untick one to stop offering it to the model in chats on this routing.
  10. Save checks the routings first: anything that has to be fixed is listed in a box at the bottom right, and the boxes it is in turn red with the reason written inside. Then it writes each change where it belongs and tells you what it saved. The Router and Interceptor use changes on the next request. Restart the Gateway (LiteLLM) after changing models or fallbacks. Discard changes goes back to what is saved.

Hover over anything on this page for a short hint. With Show live requests on, each request's path lights up green as it goes through. Box positions are kept in this browser; Tidy layout lays them out again along the lines of the routing shown.

Save writes the Router's choices to its config file, the Interceptor's to harness-settings.json, and models and fallbacks to config.yaml, keeping its comments. Other classifier settings are on the Settings page.
